# Week 2 WIL

이번 주에는 DDD(Domain-Driven Design)의 기본 개념인 Value Object, Aggregate, Aggregate Root, Invariant에 대해 배웠다.

DDD는 모든 프로젝트에서 무조건 사용하기보다는 비즈니스 규칙이 복잡하고 도메인이 중요한 프로젝트에서 효과적이라고 생각했다. 예를 들어 커머스에서는 주문, 결제, 재고, 배송, 환불처럼 서로 연관된 규칙이 많고, 금융 서비스에서도 송금, 잔액, 거래와 관련된 규칙을 정확하게 지켜야 한다. 이런 프로젝트에서는 단순히 Service에 모든 로직을 작성하는 것보다 각 도메인 객체가 자신의 책임과 규칙을 가지도록 설계하는 DDD가 유용할 수 있다고 생각했다.

GDG 프로젝트 트랙에서도 DDD를 사용할 수 있다고 생각한다. 다만 프로젝트 규모와 복잡성을 고려해야 할 것 같다. 단순한 CRUD 위주의 작은 프로젝트라면 처음부터 복잡한 DDD 구조를 적용하는 것이 오히려 개발 속도를 늦출 수 있다. 반대로 프로젝트가 커지고 비즈니스 규칙이 복잡해진다면 일부 핵심 도메인부터 DDD의 개념을 적용해볼 수 있을 것 같다. 따라서 DDD를 사용한다는 것 자체를 목표로 하기보다 프로젝트에서 복잡한 비즈니스 규칙이 어디에 있는지를 먼저 파악하는 것이 중요하다고 생각했다.

이번 실습에서 Product의 수량을 단순한 int 대신 Quantity라는 Value Object로 표현해보면서 이러한 장점을 조금 더 이해할 수 있었다. 기존에는 Product가 수량이 1 이상인지 직접 검사해야 했지만, Quantity가 자신의 유효성 규칙을 가지도록 만들면 유효하지 않은 수량이 만들어지는 것을 처음부터 막을 수 있었다. 이를 통해 단순한 값도 도메인에서 중요한 의미와 규칙을 가진다면 하나의 객체로 표현할 수 있다는 것을 배웠다.

또한 Order와 OrderItem을 통해 Aggregate와 Aggregate Root의 개념을 배웠다. Order가 여러 OrderItem을 관리하고, 외부에서 OrderItem 목록을 직접 수정하지 못하도록 한 뒤 Order를 통해서만 변경하도록 하면 주문과 관련된 규칙을 한 곳에서 보호할 수 있다. 특히 cancelItem을 구현하면서 "주문에는 최소 하나 이상의 주문 항목이 존재해야 한다"와 같이 객체가 항상 지켜야 하는 규칙을 Invariant라고 한다는 것을 알게 되었다.

DDD의 장점은 비즈니스 규칙과 코드의 책임을 명확하게 표현할 수 있고, 복잡한 프로젝트에서도 각 객체가 어떤 역할을 담당하는지 파악하기 쉬워진다는 점이라고 생각한다. 또한 중요한 규칙을 해당 도메인 객체 내부에서 보호할 수 있기 때문에 잘못된 상태가 만들어지는 것을 방지하는 데도 도움이 된다.

반면 단점도 있다고 생각한다. 단순한 기능을 구현하는 데도 Entity, Value Object, Aggregate 등의 개념을 고려해야 하기 때문에 처음 접하면 설계가 어렵고 코드가 복잡해질 수 있다. 또한 규모가 작은 CRUD 프로젝트에 과도하게 적용하면 얻는 이점보다 개발 비용이 더 커질 수도 있다.

결국 DDD 자체가 항상 좋은 설계 방법이라기보다는 복잡한 비즈니스 규칙을 다루는 프로젝트에서 특히 가치가 있는 방법이라고 이해했다. 앞으로 프로젝트를 설계할 때 무조건 Service에 비즈니스 로직을 작성하기보다 "이 규칙은 어떤 객체가 알고 있어야 하는가?", "이 객체가 항상 지켜야 하는 규칙은 무엇인가?"를 먼저 생각해보는 습관을 들이고 싶다.
