Week5 WIL - JPA 조회 최적화와 쿼리 튜닝

1. 이번 주 학습 내용

이번 5주차에서는 JPA를 사용하면서 발생할 수 있는 N+1 문제와 이를 해결하기 위한 Fetch Join, Batch Size에 대해 학습했다.

JPA에서는 연관된 엔티티를 조회할 때 LAZY 로딩을 사용할 수 있는데, 이 경우 처음에는 필요한 엔티티만 조회하고 연관된 데이터에 접근하는 시점에 추가 SQL이 실행된다. 이 과정에서 주문 목록을 조회한 후 각 주문의 주문 항목을 하나씩 조회하면 N+1 문제가 발생할 수 있다.

이를 해결하기 위한 방법으로 Fetch Join과 Batch Size를 실습했다.

Fetch Join은 연관된 엔티티를 JOIN을 통해 한 번에 조회하는 방법이고, Batch Size는 연관된 엔티티를 조회할 때 여러 개의 데이터를 묶어서 조회하는 방법이다.

2. 주문 수 증가에 따른 SQL 개수 비교

이번 실습에서는 주문 수를 기존 10건에서 20건으로 늘리고, 주문별 항목 수는 3건, Batch Size는 10으로 설정했다.

실습 조건에서 예상되는 SQL 실행 횟수는 다음과 같다.

조회 방식	주문 10건	주문 20건
Fetch Join	1개	1개
Batch Size 10	2개	3개

Fetch Join은 주문과 주문 항목을 JOIN하여 한 번의 SQL로 조회하기 때문에 주문 수가 증가해도 SQL 실행 횟수는 1번으로 유지된다.

반면 Batch Size는 먼저 주문 목록을 조회한 후, 주문 항목에 접근할 때 설정된 Batch Size만큼 주문을 묶어 조회한다. 따라서 주문이 20건이고 Batch Size가 10이라면 주문 목록 조회 1번과 주문 항목 조회 2번으로 총 3번의 SQL이 실행된다.

이를 통해 Fetch Join은 연관 데이터를 한 번에 조회하고, Batch Size는 여러 번에 나누어 조회한다는 차이를 확인할 수 있었다.

3. Fetch Join이 항상 더 좋은 방법일까?

이번 실습에서는 Fetch Join의 SQL 실행 횟수가 더 적었지만, 그렇다고 항상 Fetch Join이 더 좋은 방법이라고 생각하지는 않는다.

Fetch Join은 한 번의 SQL로 필요한 데이터를 가져올 수 있다는 장점이 있지만, 일대다 관계에서 JOIN을 수행하면 하나의 주문 정보가 여러 주문 항목에 대해 반복되어 조회될 수 있다. 따라서 연관된 데이터가 많아질수록 조회 결과의 크기가 커질 수 있다.

반면 Batch Size는 SQL 실행 횟수가 상대적으로 많지만, 주문과 주문 항목을 나누어 조회하기 때문에 JOIN으로 인한 데이터 중복을 줄일 수 있다. 또한 컬렉션을 Fetch Join하는 방식과 달리 주문 목록에 대한 페이징을 적용하기에도 유리하다.

따라서 조회 성능을 비교할 때는 단순히 SQL 실행 횟수만 확인하는 것이 아니라 실제 조회하는 데이터의 양, 실행 시간, 페이징 필요 여부 등을 함께 고려해야 한다는 것을 배웠다.

4. 쿼리 튜닝이란?

쿼리 튜닝(Query Tuning)은 데이터베이스에서 SQL을 더 효율적으로 실행할 수 있도록 분석하고 개선하는 작업이다.

데이터베이스에 저장된 데이터가 많아지면 같은 SQL이라도 실행 시간이 길어질 수 있다. 따라서 불필요한 데이터 조회를 줄이고, 데이터베이스가 효율적으로 데이터를 찾을 수 있도록 개선하는 것이 중요하다.

대표적인 방법으로는 인덱스(Index), 페이징(Paging), 실행 계획(Execution Plan) 분석 등이 있다.

인덱스는 책의 목차처럼 원하는 데이터를 빠르게 찾을 수 있도록 도와주는 자료구조이다. 적절한 인덱스를 사용하면 테이블 전체를 조회하지 않고도 필요한 데이터를 찾을 수 있다. 하지만 인덱스가 많아지면 데이터 삽입이나 수정 시 추가적인 비용이 발생할 수 있으므로 적절하게 사용해야 한다.

페이징은 전체 데이터를 한 번에 조회하지 않고 일정한 개수로 나누어 조회하는 방법이다. 예를 들어 주문이 10만 건 존재하더라도 사용자에게 필요한 20건만 조회하면 불필요한 데이터 전송을 줄일 수 있다.

실행 계획은 데이터베이스가 SQL을 어떤 방식으로 실행하는지 보여주는 정보이다. 이를 통해 인덱스를 사용하는지, 테이블 전체를 탐색하는지 등을 확인하고 성능이 저하되는 원인을 분석할 수 있다.

결국 쿼리 튜닝은 SQL 개수를 줄이는 것뿐만 아니라 SQL 실행 시간과 조회하는 데이터의 양, 데이터베이스의 자원 사용량까지 고려하여 전체적인 성능을 개선하는 작업이라고 이해했다.

5. 마무리

이번 실습을 통해 JPA를 사용하면 객체를 통해 편리하게 데이터를 조회할 수 있지만, 실제로 어떤 SQL이 실행되는지 이해하는 것도 중요하다는 것을 배웠다.

특히 Fetch Join과 Batch Size를 비교하면서 같은 데이터를 조회하더라도 조회 방식에 따라 SQL 실행 횟수와 데이터 조회 방식이 달라질 수 있다는 점을 알게 되었다.

앞으로 Spring Boot와 JPA를 사용하여 개발할 때 단순히 기능이 정상적으로 동작하는지만 확인하는 것이 아니라, 실제 실행되는 SQL과 조회 성능까지 고려하며 개발해야겠다고 생각했다.
