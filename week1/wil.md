# Week 1 WIL

이번 실습을 통해 기존에 알고 있던 Service와 Entity의 역할에 대해 다시 생각해볼 수 있었다. 이전에는 Service가 대부분의 비즈니스 로직을 담당한다고 생각했지만, 객체 자신의 상태와 관련된 비즈니스 규칙은 Service에서 모두 처리하기보다 해당 데이터를 가지고 있는 Entity가 직접 판단하고 처리하도록 설계할 수 있다는 것을 배웠다.

이와 함께 Entity에서 Setter를 무분별하게 사용하는 것이 왜 좋지 않은지도 이해할 수 있었다. Setter를 열어두면 외부에서 Entity의 값을 직접 변경할 수 있기 때문에, Entity가 지켜야 하는 비즈니스 규칙을 거치지 않고 잘못된 값으로 상태가 변경될 수 있다. 따라서 단순히 값을 변경하는 Setter를 사용하기보다는 `decreaseStock()`과 같이 의미가 명확한 메서드를 Entity에 만들고, 그 메서드 내부에서 필요한 검증과 상태 변경을 함께 수행하는 것이 더 올바른 설계라는 것을 알게 되었다.

또한 Tell, Don't Ask(TDA)라는 개념을 처음 알게 되었다. Service가 Entity의 데이터를 가져와서 직접 판단하고 상태를 변경하기보다는, Entity에게 어떤 행동을 수행하라고 요청하고 실제 판단은 해당 데이터를 가지고 있는 Entity가 하도록 하는 방식이다. 이 개념은 앞에서 배운 Entity의 책임과 Setter 사용을 지양하는 이유와도 연결된다고 생각했다.

이전에는 테스트 코드를 많이 사용하지 않고 Swagger나 Postman을 이용하여 직접 API를 호출하면서 기능을 확인하는 경우가 많았다. 이번 실습을 통해 작성해 둔 테스트 코드는 버튼 한 번으로 동일한 검증을 반복해서 수행할 수 있다는 장점이 있다는 것을 알게 되었다. 특히 리팩토링 전후에 동일한 테스트를 실행하여 모두 통과하는지 확인하면, 내부 코드의 구조를 변경하면서도 기존 동작이 유지되는지 확인할 수 있다는 점이 인상적이었다.

이를 통해 Refactoring은 단순히 코드를 수정하는 것이 아니라, 외부에서 보이는 동작은 유지하면서 코드의 내부 구조를 개선하는 것이라는 개념도 알게 되었다. 또한 Java 테스트에서 JUnit은 테스트를 작성하고 실행하기 위한 기본적인 테스트 프레임워크이고, AssertJ는 테스트 결과를 보다 읽기 쉽고 편리하게 검증할 수 있도록 도와주는 라이브러리라는 것도 배웠다. 마지막으로 테스트 코드를 `Given - When - Then`의 구조로 작성하여 테스트를 위한 상황을 준비하고(Given), 실제 동작을 실행한 뒤(When), 예상한 결과가 나왔는지 검증하는(Then) 방식도 익힐 수 있었다.
